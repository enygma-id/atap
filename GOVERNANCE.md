# Governance

## Project

**ATAP: ATAP Terrain-Aware Architectural Polygonization**

ATAP is founded and stewarded by **Enygma**.

Legal Project Steward:

**PT Enygma Solusi Negeri**

## Principles

ATAP governance is intended to preserve:

- technical quality;
- scientific integrity;
- transparent development history;
- contributor attribution;
- licensing integrity;
- project continuity;
- security;
- official project identity.

## Project Steward

The Project Steward is responsible for:

- official project identity;
- canonical repository designation;
- governance policy;
- release policy;
- licensing policy where legally authorized;
- contributor agreement policy;
- brand and trademark stewardship;
- maintainer appointment and removal;
- security escalation;
- institutional representation;
- major strategic direction.

Project stewardship does not remove rights already granted under an applicable
open-source license.

## Roles

### Core Maintainers

Core Maintainers have review and merge authority over one or more core areas.

### Area Maintainers

Area Maintainers may be appointed for domains such as:

- polygonization core;
- raster/elevation processing;
- GIS data model;
- geometry;
- point-cloud research;
- roof/surface research;
- packaging and CLI;
- tests and benchmarks;
- documentation;
- release engineering.

### Contributors

Contributors are individuals or legal entities whose contributions are accepted
into the official project.

Contributor status does not automatically grant:

- merge authority;
- project stewardship;
- trademark rights;
- institutional representation authority;
- Enterprise licensing authority.

## Decision-Making

ATAP seeks technical consensus where practical.

General escalation order:

1. Area Maintainers resolve ordinary implementation issues.
2. Core Maintainers resolve cross-area technical issues.
3. Designated technical/research leadership resolves major architecture or
   scientific-method disputes.
4. The Project Steward resolves governance, licensing-policy, brand,
   canonical-repository, institutional, and major strategic disputes.

## Pull Requests

Once collaborative development begins, ordinary changes should normally use
Pull Requests, including changes authored by Enygma personnel.

Protected branches should use appropriate checks where practical.

## Scientific Integrity

Material algorithm changes should document:

- motivation;
- assumptions;
- parameter changes;
- expected behavior;
- validation method;
- known limitations;
- failure cases;
- reproducibility instructions.

Novelty, accuracy, LoD, standards-conformance, or performance claims should not
be introduced without sufficient evidence.

## Licensing

Covered Community Edition source is released under `AGPL-3.0-only`.

Alternative licensing may be offered only where PT Enygma Solusi Negeri has
sufficient legal rights.

External contributions may require an auditable CLA acceptance.
